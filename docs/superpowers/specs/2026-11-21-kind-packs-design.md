# Kind packs: generic project kinds for dev-studios

Date: 2026-11-21. Status: draft, awaiting approval.

## Intent and why

dev-studios is a game-studio framework (49 game agents, `genres/`, `engines/`).
The owner also builds services and applications and wants the same framework to
give those projects proper design discipline.

The trigger is pinkie, an OpenCode-based agent setup generated by `ai-init`
(`agent-init/init-agents.sh`). Today ai-init installs only model-tier routing
roles: orchestrator, planner, reader, three implementors, reviewer, committer.
It installs no design role, no skill and no gate. In one 7-hour session pinkie:

1. Built a feature the owner had said would not work (user constraint ignored).
2. Never ran the idea on a representative sample before planning slices. The
   fixture turned out to be Redshift only after the dialect decision was made.
3. Chose a test repo it already knew had no DDL, and said so only afterwards.
4. Planned multi-hour slices with no premise check.
5. Ignored the owner's output-style rule (ADHD formatting) until told off.

Goal: a `kind` in dev-studios, with a pack of roles and skills per kind, that
`ai-init --kind <name>` installs into a target repo so these failures are
prevented by the workflow, not by the owner's vigilance.

## Goals

- `kind` values: `game` (default, current behaviour), `service`, `application`,
  `generic`.
- dev-studios is the single source of truth for pack content.
- `ai-init --kind <name>` installs the pack into a repo's `.opencode/agents/`
  and `.opencode/skills/`, and lists it in the managed `AGENTS.md` block.
- The orchestrator flow enforces the gates, not just documents them.

## Non-goals

- No new models and no model-tier changes.
- No change to the game pack, genres or engines.
- No per-repo design content (ADRs, contracts) shipped in the pack.
- No attempt to make dev-studios skills run unchanged under OpenCode.

## Anti-goals

- A pack that is only prose. A skill the orchestrator never routes through is a
  failure even if it ships.
- Breaking existing game projects: absent `kind` must behave exactly as today.

## Constraints

- `kind` is already listed as a locked project-identity key in
  `.claude/docs/effects-map.md` (line 136) but nothing defines or reads it. Use
  that slot; do not introduce a second key.
- dev-studios rules: `project.yaml` is the config store, resolved via
  `resolve_config`; do not seed the six knobs `modes.rigor` fronts.
- OpenCode loads skills from `.opencode/skills/<name>/SKILL.md` (verified in
  `opencode/packages/web/src/content/docs/skills.mdx`).
- ai-init stages all output in a temp dir and writes through `write_file`;
  re-running regenerates managed files. Pack files must go through that path.
- pinkie builders cannot edit `.opencode/`, `opencode.json`, `AGENTS.md`,
  `.claude/` or `.codex/`. Installed content is therefore only changed by
  re-running ai-init.
- ai-init lives in the local arcane clone at
  `/Volumes/Engineering/Kodeniks/arcane/projects/hindsight/agent-init/`
  (`init-agents.sh`, `routing.md.tmpl`). Editing the local clone is fine (owner
  confirmed); do not edit on the Proxmox server unless needed, and changes sync
  to git from the local clone. The orchestrator, planner and other role prompts
  are heredocs inside `init-agents.sh`.
- Gates follow dev-studios' own gate model (owner decision, see Enforcement):
  reuse `modes.rigor` tiers, stage gates and director-style review rather than
  inventing a new mechanism.
- The owner's global CLAUDE.md applies: no AI attribution trailer in commits
  (memory: feedback_no_ai_attribution), no commits without being asked.

## Approaches considered

| | Approach | Trade-off |
|---|---|---|
| A (chosen) | `kind` key plus packs in `.claude/kinds/<kind>/` in dev-studios; ai-init copies a pack in. | One source of truth, reusable per new service. More upfront work than B. |
| B | Roles and skills written directly into ai-init; dev-studios gets only the key. | Fast, but duplicates design content and dev-studios gains nothing. |
| C | Fork a separate software studio. | Duplicates 49 agents for little gain. |

The owner picked A.

## Design

### 1. dev-studios

- `project.yaml`: add `project.kind`, one of `game | service | application |
  generic`. Absent means `game`. (builder: confirm the exact key path against
  `effects-map.md` and `config-resolution.md`; the doc names `kind` under
  `project.*`.)
- New tree `.claude/kinds/`:
  - `_software/` shared base for `service`, `application`, `generic`.
  - `service/`, `application/`, `generic/` each add only their extras.
  - Each pack holds `agents/*.md`, `skills/<name>/SKILL.md`, `rules.md` and a
    `pack.yaml` manifest listing its files and the base it extends.
- `game` has no pack directory; it keeps using the existing agents and skills.

### 2. Pack content (`_software` base; kept small on purpose)

Roles (none writes product code; they may write markdown under `docs/design/`
in the target repo, nothing else):

- `architect`: owns the design record; decides boundaries, data flow, contracts.
- `requirements-owner`: turns the request into stated goals, non-goals and
  constraints; keeps the list of owner-stated constraints.
- `design-reviewer`: reviews the design record and each slice against it; not
  the model that wrote it.

Skills, each aimed at one observed failure:

- `premise-check`: before slicing, run the proposed approach on a small
  representative sample and read the result. Pick a sample that can exercise the
  approach; if the obvious sample cannot, say so and pick another before
  building. Output: one paragraph of evidence in `docs/design/`. Who runs it
  (my call): the architect writes the sample and the success criteria, `reader`
  checks them against the real files, and anything that needs running code is a
  throwaway builder spike through `check.sh`.
- `user-constraints-binding`: any constraint the owner states is binding. On
  conflict, stop and re-plan; do not argue or build around it.
- `adr-first`: one short design record before the first slice; the planner may
  not slice without it.
- `output-style`: apply the owner's declared output rules from turn one.

`service` extras (starting set): API contract and failure-mode checklist.
`application` extras (starting set): state/data-flow and UX-flow checklist.
`generic`: base only.

### 3. ai-init

- New flag `--kind NAME` (single value).
- New flag `--studio-dir DIR`, default `$DEV_STUDIOS`, pointing at dev-studios.
- With `--kind`, ai-init resolves `_software` plus the named pack from
  `<studio-dir>/.claude/kinds/`, stages agents into `.opencode/agents/` and
  skills into `.opencode/skills/<name>/SKILL.md`, and adds a table of them to
  the managed block in `AGENTS.md`.
- Without `--kind` ai-init behaves exactly as today: the `--dry-run` output and
  the staged files are byte-identical to the current script (the parity test).
- The managed `AGENTS.md` block records the kind and the list of installed pack
  files (my call). A re-run without `--kind` reuses the recorded kind. A re-run
  with a different `--kind` deletes the files the old pack installed.
- Optional `--style-file FILE` copies the owner's output-style rules into the
  target repo for the `output-style` skill (my call). Owner constraints live in
  `docs/design/constraints.md`, kept by `requirements-owner`.
- Fails with a clear message if the pack or studio dir is missing.
- `--dry-run` lists the pack files it would write.

### 4. Enforcement

Owner decision: follow the dev-studios gate model, which the owner finds well
balanced. Do not invent a new gate system. Mapping:

- **Stages.** dev-studios `/gate-check` moves a project through stages with
  PASS / CONCERNS / FAIL verdicts. Software kinds get an adapted stage list
  (starting set, builder to refine): Concept, Design, Technical Setup, Build,
  Harden, Release. The current stage is recorded in the target repo.
- **Rigor tiers.** Reuse `modes.rigor` (`minimal | standard | full`) and its
  expansion to `modes.workflow`, as in `.claude/docs/workflow-modes.md`:
  `minimal` needs the premise-check evidence and a decision log; `standard`
  adds ADRs for critical decisions; `full` adds ADRs for all decisions and the
  kind's contract or flow checklist. Default tier is `minimal`, as today.
- **Artifact check.** A script in the target repo,
  `.opencode/scripts/gate.sh`, prints which required artifacts for the current
  stage and tier exist and which do not. It reports observations, never a
  verdict (the dev-studios convention for `.claude/scripts/` helpers). The
  orchestrator must run it before dispatching the planner or any builder.
- **Verdict.** `design-reviewer` plays the director-gate role: it reads the
  gate.sh output and the design record and returns PASS / CONCERNS / FAIL. The
  planner does not write briefs without a PASS or an owner-accepted CONCERNS.
  A reviewer is never the author of what it reviews.
- **Order.** requirements-owner, then `premise-check`, then architect writes
  the design record, then gate, then planner slices, then builders, then
  design-reviewer plus the existing code-reviewer on each slice.
- **Permissions.** Orchestrator, planner and the new roles may use the `skill`
  tool; builders may read the design record.
- **Done means** the three scripted failure scenarios from the 7-hour session
  (constraint ignored, fixture mismatch found late, unrepresentative sample)
  are each stopped by a gate when replayed, plus the parity test above.

## Left to the builder

- Exact skill and role wording.
- OpenCode permission syntax for the `skill` tool and any frontmatter fields.
- Where the design record lives in a target repo (suggest `docs/design/` in
  the target repo; marked as a suggestion).
- Tests for the ai-init flag (dry-run listing, missing pack, no-flag parity).
- Whether `pack.yaml` is needed or a directory listing is enough.
- A `/setup-kind` style entry point in dev-studios, if the existing
  `/start` and `/setup-engine` flow needs one for non-game kinds.

## Open risks

- Skill wording that is clear to a human but too weak to bind a cheap model.
  Mitigation: the enforcement lives in the orchestrator and planner prompts,
  not only in skills.
- dev-studios agents and skills assume game vocabulary; the base pack must not
  import them by reference.
